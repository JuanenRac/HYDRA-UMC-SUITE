UNLIKE every other mesh set in this project (a manufacturer's own
pre-made STL files, downloaded verbatim), LumenPnP ships no STL at all in
this source tree and has zero native FreeCAD Assembly::/Joint objects -
it's a flat grouped-parts CAD file, not a parametric robot assembly. These
7 files were generated by this project's own author, opening the real
assembly.FCStd headless (FreeCAD 1.1's own Python API, no GUI, no manual
joint-clicking) and re-grouping ~700 real, exactly-positioned CAD parts
into 7 rigid-body merges matching the machine's own real kinematic
structure - determined by reading every leaf part's own real bounding box
(e.g. GT2BeltClamp's bbox tracks the toolhead's own X position exactly,
so it's grouped with the moving X-carriage; X-Motor's bbox stays fixed
regardless of toolhead position, so it's grouped with the Y-carriage
bridge instead), not guessed. Same grouping as this project's own formal
lumenpnp_juanenpnp.urdf (7 links/6 joints).

Real fix 2026-09-08: the original cut merged each Z-carriage housing with
its own nozzle into ONE rigid body per side (z_carriage_n1/n2) - convenient
for the triangle-budget problem below, but a real visible error: the
housing's own real footprint at that joint is ~44x51mm (measured off the
per-part CAD bounding box), so the whole rectangular slider block visibly
spun around the Z axis every time a nozzle rotated, which the real machine
never does (only the ~10x10mm nozzle barrel itself spins). Split into
z_carriage_left/right (translate only) + nozzle_left/right (rotate only,
same joint origin as their z_carriage parent) - matching the URDF's own
already-correct link split - fixes it.

Two real problems surfaced only by testing this against the actual live
dev server (not assumed from file size alone), each requiring a real fix
rather than a bigger number:

1. Triangle budget. The first honest export (every part down to washers,
fine CAD tessellation) ran past 800MB for the base group alone - orders
of magnitude past what any other robot mesh in this app needs (e.g.
ur5classic's entire 7-part arm is 284KB total) - and even after repeated
tessellation-only cuts, still hit ~40MB / ~840K triangles combined, well
past that same working-precedent scale. The base group's own single
biggest offender (~281K of ~500K facets, found by tessellating each
base_roots entry in isolation and comparing) was Group027 ("control-box"
- the electronics enclosure, including a modeled motherboard PCB): a
mostly-hidden internal part whose small repeated features (connectors,
mounting bosses) each demand their own minimum triangle count regardless
of how coarse the tessellation deflection is set, for zero payoff at any
zoom level this viewport is used at - dropped entirely. Combined with a
much higher minimum-kept-part size (real fasteners AND now most brackets
under ~30-250mm depending on the group, up from the original 15mm),
final counts land at base ~32.6K / y_carriage ~23.9K / x_carriage ~19.2K
triangles. z_carriage_left/right (~15.2K/13.8K, kept at their real CAD
export size - already inside this same budget, no further cut needed) and
nozzle_left/right (~7.9K each, smaller than every other part) were added
2026-09-08 replacing the old merged z_carriage_n1/n2 (~5.5K each) - a
recognizable silhouette, not a bolt-for-bolt replica, still in the same
ballpark as this app's other robot meshes.

2. Runtime merge cost. Even at reduced counts, loading several raw .stl
files through STLLoader + client-side mergeVertices() (this app's
standard pattern for every *Arm.tsx mesh) still hit a real
"THREE.WebGLRenderer: Context Lost" in live testing, verified via headless
Chromium against the dev server - a plain robot arm never does this. The
cause: several synchronous mergeVertices() calls landing in the same React
commit right as all the STL fetches resolved together blocked the main
thread long enough in one burst to trip the browser's own GPU-hang
watchdog, and the resulting blank canvas never recovered on its own (no
"webglcontextrestored" fired even 40+ seconds later - this project's
Canvas has no restore handler, so once lost it stays lost). Fix: the
.stl files are kept alongside the .glb ones as the source of truth,
pre-merged/indexed offline into .glb so the browser has nothing left to
compute on load, just a buffer to upload - LumenPnPRig.tsx itself only
ever loads the .glb files. The original 5-part conversion used
three.js's own STLLoader+mergeVertices()+GLTFExporter in a browser tab;
regenerating z_carriage_left/right and nozzle_left/right 2026-09-08 used
a Node-side equivalent instead (three.js's mergeVertices() on a hand-
parsed binary STL, then a minimal hand-written, spec-valid single-mesh
GLB writer - POSITION/NORMAL/indices only, no material/image, round-trip
verified through three.js's own real GLTFLoader) because GLTFExporter
itself depends on browser-only globals (FileReader) that never resolve
under plain Node - either tool produces the same real, indexed glTF
2.0 binary, so all 7 files stay interchangeable and can be regenerated
with whichever one is convenient at the time.

Real axis travel limits (LumenPnPRig.tsx's own X/Y ranges) come from this
same repo's own openpnp/machine.xml (the real machine's own OpenPnP
control-software config), not a guess: X 0-433mm, Y 0-487mm. Z's own
soft limits in that file are disabled in favor of a safe-zone check, so
this project's own 0-90mm Z range is an estimate from the real CAD's own
Z-carriage rail length instead of a quoted spec.

JuanenPnP (this project's own author's build) shares this exact mesh set
and kinematic rig - per the author's own confirmation, it is visually and
mechanically identical to stock LumenPnP v4.

parts/ subfolder (47 additional real, individually-named CAD parts, added
alongside the 7 rigid-body groups above)

The 7 groups above stayed a "recognizable silhouette" cut - correct for
the moving assemblies, but they left several real, visually-significant
parts out entirely (most notably the machine's own 4 legs and its control
box, both requested explicitly). Rather than re-fusing those into the 7
existing groups (which is exactly what produced the original 800MB/44MB
base_link problem this file already documents above), each of these 47
parts is exported and shipped as its own small, individually-loaded
file - both because that is what keeps each one small and fast to
tessellate/render on its own, and because it lets real machine detail
(legs, control box, V-slot frame extrusions, top/bottom cameras and ring
lights, all 6 real strip-feeder sizes, the vacuum pump, a solenoid valve,
the nozzle rack, 2 nozzle holders, the X/Y gantry brackets and idler/motor
mounts) be added without ever re-touching the 7 existing files.

Selection: every part here is a real, distinctly-modeled part in Opulo's
own pnp/cad/FDM, pnp/cad/MISC or pnp/cad/PCB source folders (i.e. a real
printed part or a real purchased/PCB component with its own CAD file,
never a raw fastener) - chosen from the ~86 distinct part types in those
3 folders for real visual significance at this viewport's scale. Tiny
repeated hardware this rig will never zoom in on (all ~30 individual
Y-axis drag-chain links, all 16 individual extrusion cable clips, the
full internal motherboard PCB fused with the control box) was left out on
the same "no payoff at any zoom level this viewport is used at" basis the
first cut above already used for its own Group027 exclusion - not a
guess, the same real precedent already on this file. One part,
static-camera-foot, was tried and dropped: its own real CAD carries
71,896 pre-tessellated facets regardless of the LinearDeflection passed
to MeshPart.meshFromShape() (a Mesh::Feature-backed part, not a plain
B-Rep solid - deflection has no effect on those), producing a 5MB+ .glb
for one small decorative foot bracket; not worth the payload.

Placement: each part's own Shape is already in the real assembly's own
absolute world-space (same "flat grouped-parts CAD file" structure this
file already documents - Opulo's own object tree has no nested Assembly/
Product placement stacking, every leaf's own Placement is already
absolute), so every part here is exported and rendered exactly like the 7
groups above: identity local transform, real assembled offset baked
straight into the mesh.

Which of the 3 existing links (base_link / y_carriage / x_carriage) each
part was attached under was decided by real mechanical role, following
this file's own established precedent above (X-Motor: "bbox stays fixed
regardless of toolhead position, so it's grouped with the Y-carriage
bridge instead") rather than a naive bounding-box-overlap heuristic (which
was tried first and rejected here: at this CAD file's own modeled
rest/home pose the y_carriage group's real bbox is large enough to
spatially contain most of the static frame too, so raw AABB overlap alone
mis-bucketed several legitimately-static parts into y_carriage). Legs,
their extensions, the control box and lid, the 7 V-slot frame extrusion
segments, both cameras, both ring lights, both light mounts, the aux
staging-plate foot, all 6 feeders, the vacuum pump, the solenoid valve,
the nozzle rack, both nozzle holders and the XY limit switch board are
static → base_link. The X-idler-mount, X-motor-mount, both Y-gantry
carriage blocks, the Y-limit striker and the squaring bracket are all
fixed to the Y-bridge's own ends → y_carriage (moves in Y only, same
X-Motor precedent). The toolhead's own front/back gantry plates
(x-gantry-back/front) slide along the beam in X → x_carriage.

47 parts, combined ~9.3MB across all .glb files (avg ~200KB/part,
matching this viewport's existing per-part budget), tessellated the same
way as the 7 groups above (MeshPart.meshFromShape(), coarser
LinearDeflection overridden per-part only where a part's own real facet
count demanded it - control-box/-lid and both ring lights, all real
per-part decisions logged in this same folder's parts/manifest.json
alongside every part's own real CAD source label, assembled bounding box
and triangle count) and converted to .glb the same Node-side way
documented above (binary STL parsed by hand, vertices welded, a minimal
hand-written spec-valid GLB written directly - no browser-only globals).

parts/ batches 2-4 (2026-09-08, same day as the batch above - added after
the user looked at the live rig and named specific real gaps: motors,
pulleys, the drag chain, belts, then asked for more individualized
mechanical parts beyond fasteners)

Batch 2 (motors/pulleys/idlers/drag chain, 46 parts): the 2 real Y
motors (NEMA17-stepper) are bolted to the fixed frame at the rear -
they drive belts, they don't ride the bridge - same for their own
rear pulleys and the front idlers that close each belt loop. The X
motor is mounted ON the Y-bridge (same real precedent already used
above for x-motor-mount itself), and the toolhead carries its own
small stepper for the nozzle/blade drive. The real Y-axis drag chain
(30 individually-numbered links + 4 end connectors, all ~1.5-2K
triangles each - cheap) is rendered as one rigid attachment to the
bridge rather than a procedurally-folding chain; this rig has no
cable-chain physics anywhere, same simplification already accepted
for every other static part here. One real tessellation problem found
and fixed: the 4 GT2-idler parts hit 20,284 triangles / ~1MB each at
this file's own default deflection (0.25) - a bearing-like curved
part, not flat brackets like everything else - re-exported at a
coarser 0.9/0.7 deflection, down to 11,084 triangles / ~554KB each.

Batch 3 (belts/tension-arms/belt-clamps, 13 parts): the Y belt loops
(both sides) run frame-pulley to frame-idler and are fixed; their own
tension arms sit right next to those same frame idlers. The X belt
loop and its tension arm are on the bridge; the Z belt loop and its
belt-clamps are on the toolhead.

Batch 4 (rails/carriages/staging plates/fiducial board/blade
mechanisms/cable clips, 28 parts - 30 exported, 2 dropped): the fixed
Y-axis side rails (550mm-MGN12H) don't move, only their carriages
(MGN12H-linear-rail-carriage, mounted on the bridge) do; the moving
X-axis rail (525mm-MGN12H) is mounted ON the bridge, unlike the fixed
Y rails. The toolhead carries its own Z-axis rails/carriages
(mgn9-linear-rail-carriage, linear-rail-100mm) and side plates. Two
real parts were tried and dropped for the same reason Group027 (the
control-box's own mobo) was dropped in the very first cut above:
blade12-PCB_003 and blade13-PCB002 (the 2 blade-feeder mechanisms' own
PCBs) hit 161,173 and 65,606 triangles respectively - 8MB and 3.3MB -
fine copper-trace geometry with no payoff at this viewport's scale;
the blade mechanisms' own mechanical bodies (blade12_004/blade13_003,
~8.3K triangles each) were kept.

134 parts total across all 4 batches, ~20.7MB combined .stl (smaller
as .glb - see parts/manifest.json for every part's own real CAD source
label, assigned link, assembled bounding box and triangle count).
